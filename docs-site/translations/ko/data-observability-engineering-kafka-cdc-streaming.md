# Kafka·CDC·스트리밍 복구

주문은 결제 완료인데 매출 보고서에는 아직 대기로 표시된다. 분석용 사본에도 바뀐 상태를 반영해야 한다.

**CDC**는 **Change Data Capture**, 즉 변경 데이터 캡처다. DB의 추가·수정·삭제를 수집해 다른 시스템에 반영한다. 전체 행을 반복해서 복사하는 부담을 줄일 수 있다.

각 도구가 맡는 일은 다르다.

- **Debezium**은 지원되는 DB에서 변경을 읽는다.
- **Kafka**는 이렇게 만든 이벤트를 보관하고 전달한다.
- **스트림 처리기**는 이벤트를 읽어 결과를 갱신한다.

주문을 수정했다고 새 매출이 생기는 것은 아니다. 소비자는 변경을 보고서에 어떻게 반영할지 정해야 한다. 다음 장에서는 적재한 데이터를 변환하는 dbt를 배운다.

이번에는 처리기가 이벤트를 읽은 뒤 진행 위치를 기록하기 전에 멈췄다고 생각해 보자. 이 장에서는 작업을 놓치거나 두 번 계산하지 않도록 복구하는 방법을 살펴본다.

## 이 장에서 처음 쓰는 말

| 용어 | 의미 | 왜 필요한가요 · 언제 쓰나요 |
|---|---|---|
| 파티션 / 오프셋 | 파티션은 Kafka 로그를 순서대로 쌓는 구간이다. 오프셋은 그 파티션 안의 위치를 가리킨다. | 순서가 보장되는 범위와 장애 후 다시 읽을 위치를 구분한다. **구체적인 상황(가상 예시):** Kafka 소비자가 장애 후 이어서 처리해야 한다. → 파티션별 읽기 위치를 기록하고 복구한다. → 오프셋 커밋 경계에 맞게 재처리와 중복 처리가 되는지 확인한다. |
| 소비자 그룹(consumer group) | 토픽의 파티션을 나누어 읽는 소비자들의 그룹이다. | 여러 소비자가 파티션을 나눠 처리하게 한다. **구체적인 상황(가상 예시):** 소비자 하나가 토픽 처리량을 따라가지 못한다. → 파티션 병렬성 한도 안에서 같은 그룹에 소비자를 추가한다. → 선형 확장을 가정하지 말고 할당과 지연을 확인한다. |
| 재균형(rebalance) | 소비자가 들어오거나 나갈 때처럼 파티션 담당을 소비자들 사이에서 다시 나누는 것이다. | 소비자가 추가되거나 멈췄을 때 담당을 넘기고 처리를 이어 간다. **구체적인 상황(가상 예시):** Kafka 소비자를 추가하자 파티션 담당 프로세스가 바뀐다. → 그룹 재균형을 관찰하고 할당 회수를 안전하게 처리한다. → 처리되지 않은 중복이나 진행 위치 유실 없이 재개되는지 확인한다. |
| CDC | 변경 데이터 캡처다. DB의 추가·수정·삭제를 기록해 다른 시스템에도 반영할 수 있게 한다. | 원본 전체를 매번 복사하지 않고 바뀐 행으로 분석용 사본을 갱신한다. **구체적인 상황(가상 예시):** 주문이 결제 대기에서 완료로 바뀌었는데 분석 화면에는 대기로 남아 있다. → DB 변경을 포착해 주문 식별자로 분석 저장소에 반영한다. → 반영 지연을 확인하고 재전송해도 주문이 늘지 않는지 확인한다. |
| 이벤트 시간 / 처리 시간 | 이벤트 시간은 사건이 실제로 발생한 시각이다. 처리 시간은 시스템이 그 기록을 다룬 시각이다. | 늦게 도착한 기록을 어느 시간대의 보고서에 넣을지 정한다. **구체적인 상황(가상 예시):** 휴대전화가 오프라인에서 발생한 이벤트를 한참 뒤 업로드한다. → 발생 시각과 도착·처리 시각을 따로 보존한다. → 보고서가 의도한 업무 시각 기준으로 집계하는지 확인한다. |
| 워터마크(watermark) | 관측한 이벤트 시각을 바탕으로 계산한 경계다. 지원되는 스트리밍 연산에서 늦은 데이터와 보존할 상태를 판단할 때 쓴다. | 늦은 이벤트를 언제까지 반영하고 이전 집계 상태를 얼마나 보관할지 정한다. **구체적인 상황(가상 예시):** 지난 스트리밍 구간에 해당하는 이벤트가 계속 늦게 도착한다. → 엔진이 지원하는 워터마크와 지연 데이터 정책을 정한다. → 허용 지연 경계의 양쪽 이벤트를 시험한다. |
| 체크포인트(checkpoint) | 장애 후 다시 시작할 때 사용할 수 있도록 저장한 진행 위치와 처리 상태다. | 장애 후 처음부터 시작하지 않고 저장한 위치와 상태에서 이어서 처리한다. **구체적인 상황(가상 예시):** 상태를 가진 스트리밍 잡이 실패 후 재시작한다. → 설정한 체크포인트에서 진행 위치와 상태를 복구한다. → 소스 재생과 싱크 동작이 의도한 처리 계약을 지키는지 확인한다. |

## 먼저 이해하기

1. 생산자는 원하는 순서 범위를 보존하는 키 등을 사용해 파티션을 선택한다.
2. Kafka는 설정된 승인·복제 정책에 따라 레코드를 추가한다.
3. 소비자나 스트림 처리기가 위치를 읽고 상태를 갱신한다.
4. 출력 대상이 영속 결과를 커밋한다.
5. 복구 시 기록된 진행 상태부터 재개하고 다시 읽을 수 있는 레코드를 처리한다.

Kafka 순서는 파티션 범위다. 파티션을 늘려도 전역 순서는 생기지 않으며 키 배정 방식이 달라질 수 있다. `acks`·복제·동기 복제본 정책은 브로커 내구성을, 생산자 멱등성은 지원되는 재시도 중복을 다룬다. 어느 쪽도 데이터베이스 쓰기나 HTTP 부수 효과를 자동으로 정확히 한 번 만들지 않는다.

## 트랜잭션 경계 그리기

```mermaid
sequenceDiagram
  participant K as Kafka
  participant P as Processor
  participant T as Table sink
  K->>P: event e42 at offset 91
  P->>T: commit e42
  T-->>P: committed
  Note over P: crash before progress is durable
  K->>P: replay e42 after recovery
  P->>T: reconcile or deduplicate e42
```

Kafka 트랜잭션은 요구되는 소비자 동작 아래 Kafka 출력과 소비 오프셋을 함께 조정한다. 외부 출력에는 호환되는 자체 트랜잭션·멱등 프로토콜이 필요하다. Spark 문서는 출력별 보장을 구분한다. Kafka sink는 최소 한 번이며 `foreachBatch`도 적절한 중복 제거를 구현하지 않으면 기본적으로 최소 한 번이다. 체크포인트만으로 모든 출력이 정확히 한 번이 되지는 않는다.

## CDC에는 소스 계약이 필요하다

Debezium PostgreSQL 커넥터는 초기 스냅샷과 논리 디코딩을 통한 데이터베이스 변경을 읽는다. 복제 슬롯, WAL 보존, 소스 위치, 트랜잭션 메타데이터, 삭제 이벤트, 재시작 동작을 학습한다. 멈춘 커넥터 때문에 소스에 WAL이 쌓일 수 있으므로 이 저장 위험은 Kafka 소비자 지연과 별도로 감시한다.

애플리케이션의 “주문 결제 완료” 이벤트는 업무에서 일어난 일을 표현한다. CDC의 “행 갱신” 기록은 DB에 저장된 값이 바뀌었다는 뜻이다. 둘을 같은 것으로 처리하면 주문 수정이 새 매출로 집계될 수 있다. 삽입·갱신·삭제를 분석용 행에 어떻게 반영할지 정하고, 여러 변경을 함께 반영해야 하는 트랜잭션도 구분한다. 초기 스냅샷과 이후 변경에 같은 행이 나타나더라도 비교할 수 있도록 소스 식별자를 보존한다.

스키마 레지스트리는 설정된 호환성 정책을 검사한다. 그대로인 정수 필드의 단위가 센트에서 달러로 바뀐 의미는 추론하지 못한다. 데이터 계약에서 단위·업무 의미를 버전 관리하고 전환 중 이전·새 소비자를 함께 시험한다.

## 이벤트 시간과 상태

10:01에 발생해 10:12에 도착한 이벤트가 10:00~10:05 집계에 미칠 영향은 지연 도착 정책과 연산 종류·출력 모드에 달려 있다. 워터마크는 관측 이벤트 시간과 설정에서 추정한 진행 상태이며 모든 생산자가 다 보냈다는 증거가 아니다. 조용한 파티션, 시계 오류, 순서가 바뀐 레코드를 명시적으로 처리한다.

Spark Structured Streaming은 흔히 마이크로 배치를 사용하는 증분 DataFrame 모델이다. Flink는 연속 이벤트 시간 처리, 워터마크, 키별 상태, 체크포인트를 비교하는 데 유용하다. 측정한 지연, 상태 크기, 커넥터 동작, 운영 역량으로 선택한다. 제품 이름만으로 종단 간 의미가 보장되지는 않는다.

## 복제·ISR·승인·순서

파티션마다 리더와 복제본이 있다. ISR은 Kafka 규칙상 충분히 따라잡았다고 간주하는 복제본 집합이다. 복제 계수 3, `min.insync.replicas=2`, 생산자 `acks=all`이면 설정된 최소 ISR 조건을 만족하고 현재 동기 복제본 집합의 승인이 필요하다. `acks=all`은 정확히 두 복제본이나 오프라인까지 포함한 모든 설정 복제본을 뜻하지 않는다. ISR이 최소값보다 줄면 요구를 조용히 약화하는 대신 쓰기가 실패한다.

반면 `acks=1`은 같은 복제 대기 없이 리더 승인만 기다리므로 복제 전 리더가 죽으면 승인한 레코드를 잃을 수 있다. `acks=0`에서는 생산자가 브로커 승인을 받지 않는다. 복제본 장애 중 가용성과 내구성 요구를 비교하고 브로커·생산자 설정을 함께 기록한다. 한 정책에서 전송 성공했다고 다른 정책의 보장이 입증되지는 않는다.

생산자 멱등성은 순번 정보를 붙여 지원되는 재시도 레코드를 브로커에서 중복 제거하게 한다. Kafka 4.1은 `acks`, 재시도, 최대 처리 중 요청 사이의 필수 관계를 문서화한다. 이는 다른 이벤트 식별자를 가진 업무 요청 둘을 합치지 않으며 소비자의 HTTP 요청을 멱등하게 만들지도 않는다. 업무 이벤트 ID는 Kafka 오프셋과 독립적으로 보존한다.

순서는 파티션 로그 안에서 유지된다. 선택한 파티셔너로 고객별 키를 쓰면 관련 이벤트가 모이지만 매우 활발한 고객 하나가 그 파티션을 포화시킬 수 있다. 파티션 증설은 이후 레코드의 키 배치를 바꿀 수 있어 증설 전후 순서에는 전환 설계가 필요하다. 같은 파티션의 레코드를 독립 워커에 보내면 Kafka 전달 순서가 맞아도 완료 순서는 바뀔 수 있다.

## 소비자 할당·재균형·지연

일반적인 소비자 그룹 구독에서는 파티션 하나를 동시에 한 그룹 구성원에게 할당한다. 파티션 6개·소비자 3개면 각각 두 개가 될 수 있고 소비자 8개면 일부는 할당받지 못한다. 다른 그룹은 같은 로그를 독립적으로 읽는다. 멤버나 구독이 바뀔 때 할당 전략·재균형 프로토콜이 소유권 변경 방식을 정하므로 모든 클라이언트가 같은 세대의 동작을 쓴다고 가정하지 않는다.

파티션 담당이 바뀌면 이전 소비자는 넘겨준 파티션의 새 작업을 시작하지 않아야 한다. 이미 시작한 작업을 정리한 뒤 어디까지 완료했는지 기록한다. 예를 들어 오프셋 101과 103은 끝났지만 102가 미완료라고 하자. 다음 읽을 위치를 104로 기록하면 재시작 후 102를 건너뛴다. 이 방식에서는 중간에 빠진 작업이 없는 지점까지만 커밋 위치를 옮긴다.

오프셋은 위치이지 시각이 아니다. 10,000건 지연도 발생률·나이에 따라 수초나 수시간일 수 있다. 파티션별 지연, 가장 오래 기다린 미처리 이벤트의 대기 시간, 처리량, 공개 지연을 함께 본다. 아래 계산은 다음 위치 관례와 빈틈 없는 로그를 가정한 예시다.

```text
partition 0: end position=1000 committed next position=900 lag=100
partition 1: end position=2000 committed next position=1990 lag=10
group lag=110, but partition 0 determines most catch-up work
```

자동 커밋 시점이 실제 처리 완료보다 앞설 수 있으므로 메시지를 읽는 주기와 처리 순서를 함께 설계한다. 위치를 먼저 커밋하고 DB 반영 전에 멈추면 재시작 후 그 메시지를 건너뛰어 결과가 누락될 수 있다. 반대로 DB 반영 후 위치 커밋 전에 멈추면 같은 메시지를 다시 읽어 중복 반영할 수 있다. 외부 저장소에는 트랜잭션이나 멱등 처리를 적용하고, 두 단계 사이에서 중단해 결과를 확인한다.

## Kafka 트랜잭션과 외부 출력 대상

Kafka 읽기·처리·쓰기 트랜잭션은 출력 레코드와 소비 오프셋을 원자적으로 포함할 수 있다. 하위 소비자는 중단된 출력을 노출하지 않도록 `read_committed` 등 필요한 격리 동작을 사용해야 한다. 안정적인 트랜잭션 식별자와 fencing은 경쟁하는 생산자 인스턴스를 다룬다. 열린 트랜잭션은 read-committed 소비자의 가시성을 늦출 수 있으므로 브로커에 바이트가 있는 위치와 소비자가 읽을 수 있는 위치는 다르다.

DB에 결과를 저장할 때는 이미 처리한 이벤트 ID를 보관하는 inbox 테이블을 둘 수 있다. 이벤트 ID 기록과 주문 갱신을 같은 DB 트랜잭션에서 처리한다. 재시도 때 이미 있는 ID라면 주문을 다시 갱신하지 않고, 이후 소스의 처리 위치를 커밋한다. 두 단계 사이에서 멈춰도 이 규칙이 유지되면 중복 반영을 막을 수 있다. [메시징 재생 실습](../../content/messaging/02-duplicate-dlq-replay-lab.md)에 구현이 있다. 중복 ID를 메모리에만 보관하면 재시작 때 사라지므로 영속 저장이 필요하다.

## CDC 레코드·삭제·스키마 호환성

Debezium 변경 레코드는 커넥터·스키마 설정에 따라 작업 종류, before/after, 소스 메타데이터를 담는다. 행 갱신이 자동으로 새 매출인 것은 아니다. 삭제는 하위 개체를 제거하거나 유효성을 끝내야 하며 after 값이 NULL이라고 버리면 안 된다. Kafka tombstone은 압축 로그의 삭제 의미도 지원하므로 업무 삭제 레코드와 구분한다.

초기 스냅샷과 이후 WAL 스트림은 일관된 소스 위치 이력으로 이어져야 한다. 복제 슬롯이 보존한 WAL을 감시한다. Kafka 소비자가 따라잡았어도 소스 커넥터가 최신이라고 입증되지는 않는다. 재스냅샷은 새 이벤트처럼 무작정 추가하지 말고 행 식별자·버전을 대조한다. 여러 행으로 된 업무 갱신을 함께 노출해야 한다면 소스 트랜잭션 묶음도 중요하다.

하위 호환성은 새 리더가 이전 데이터를 읽는 것이고 상위 호환성은 이전 리더가 새 데이터를 읽는 것이다. 정확한 규칙은 Avro·Protobuf·JSON Schema와 레지스트리 정책에 달려 있다. 기본값 있는 선택 필드는 검사를 통과할 수 있고 센트→달러 단위 변경은 그대로 놓칠 수 있다. 도메인 계약과 함께 이전·새 리더와 페이로드의 조합을 시험한다.

## Structured Streaming: 마이크로 배치와 출력 모드

마이크로 배치는 제한된 입력 구간을 선택하고 상태를 갱신해 출력한다. 체크포인트는 재개에 필요한 소스 진행 상태·상태를 기록한다. trigger 주기는 배치를 시도할 때를 정한다. 배치가 30초 걸리면 1초 trigger가 1초 완료를 만들지 않는다. 초당 입력·처리 행 수와 배치 단계별 시간을 비교한다.

Append 모드는 확정 가능한 쿼리에서 새로 확정된 결과 행을 내보낸다. Update는 바뀐 결과 행을 내보내므로 출력 대상은 반복 키가 금액 추가가 아닌 교체임을 이해해야 한다. Complete는 매 배치 전체 결과 테이블을 내보내며 집계 상태가 계속 커질 수 있다. 가능한 모드는 연산자·소스·출력 조합에 의해 제한된다.

`foreachBatch` 콜백은 이전에 시도한 배치를 다시 받을 수 있다. 안정된 쿼리·체크포인트 수명 안의 배치 식별자로 중복 제거하거나 출력에서 안정적인 이벤트·버전 키를 대조한다. 체크포인트를 초기화하면 배치 번호가 다시 시작할 수 있으므로 `batch_id`만으로 새 파이프라인 식별자 전반에 유일하지 않다. 다중 테이블 업무 공개의 절반씩 독립 커밋하면서 원자적이라고 불러서도 안 된다.

### 워터마크·윈도·늦은 수정

5분 고정 윈도 `[10:00,10:05)`와 지연 허용 10분을 생각해 보자. 엔진이 이벤트 시간 10:20을 관측하면 후보 워터마크는 10:10이다. 지원되는 집계는 이후 오래된 윈도를 확정하고 상태를 제거할 수 있다. 실제 진행 상태은 엔진의 배치·연산자 규칙을 따르며 실제로 걸린 시간 경과만으로 관측 이벤트 시간이 전진하지는 않는다.

```text
event time 10:01 arrives while window state is open: contributes to [10:00,10:05)
event time 10:04 arrives after a watermark beyond 10:05: may be too late
event time 10:20 observed: progress can advance, even if another source is delayed
```

Spark의 지연 데이터 보장은 “설정한 허용 지연보다 덜 늦은 데이터는 워터마크 때문에 버리지 않는다”는 쪽으로 해석한다. 더 늦은 데이터가 항상 버려진다는 뜻은 아니다. 상황에 따라 처리될 수도 있다. 따라서 허용 시간을 넘긴 모든 이벤트에 같은 결과를 예상하지 말고, 실습에서 사용한 연산자와 출력 모드별 동작을 기록한다.

워터마크 기반 중복 제거에도 기억 기간이 있다. 식별자가 상태에서 만료된 뒤 재시도하면 그 상태만으로 알아볼 수 없다. 금액 정확성에 전체 수명 중복 제거가 필요하면 출력에 영속적인 식별자·버전 규칙을 둔다. 스트림 간 조인은 미대응 행 상태를 제한하려면 시간 관계와 워터마크의 경계가 필요하다. 무제한 조인은 상태를 끝없이 쌓을 수 있다.

## Flink·키별 상태·체크포인트·역압

Flink는 다른 실행 모델을 비교하기에 유용하다. 이벤트가 연산자를 흐르고 키 기반 분배가 상태를 해당 인스턴스에 두며 워터마크가 이벤트 시간 진행 상태을 전달한다. 다중 입력은 흔히 관련 워터마크 중 가장 느린 것에 맞춰 전진한다. 유휴 처리가 없으면 조용한 소스가 진행 상태을 막을 수 있으므로 소스 활동을 CPU와 따로 감시해야 한다.

체크포인트 장벽은 스트림에 넣는 표식이다. 각 연산자가 이 표식을 기준으로 상태를 저장해, 장애 후 소스 위치와 처리 상태를 맞춰 복구하도록 돕는다. 결과 저장까지 원하는 수준으로 보장하려면 출력 대상도 호환되는 트랜잭션·복구 방식을 지원해야 한다. 상태가 크거나 뒤쪽 처리가 느리면 체크포인트 완료도 늦어진다. 마지막 완료 이후 지난 시간과 저장 소요 시간을, 입력을 다시 읽을 수 있는 보존 기간과 비교한다.

역압(backpressure)은 하위 연산자가 상위 속도로 작업을 받을 수 없다는 뜻이다. 영속 소스 보존도 유한한 기간만 적체를 흡수한다. 초당 유입 5,000·처리 4,000이면 시간당 360만 이벤트가 쌓인다. 파티션 병렬성을 넘겨 소비자를 추가해도 해결되지 않으며 출력이 포화됐다면 소스 읽기 가속도 해결책이 아니다.

## 단계별 실패 행렬

격리 토픽, 가상 이벤트 ID, 임시 출력 대상, 독립적인 예상 입력·결과 목록를 사용한다. 문제 해결의 지름길로 실제 체크포인트를 삭제하지 않는다.

| 변경 | 예상 근거와 복구 확인 |
|---|---|
| 소비자 중지 | 지연 증가, 재시작 후 고유 대상 ID·출력값 비교 |
| 출력 커밋 뒤 중단 | 재생 발생, 업무 효과 중복 없이 출력값 대조 |
| 중복·충돌 ID 전송 | 동일 재시도 처리, 충돌 페이로드의 명시적 결과 |
| 늦은 이벤트 전송 | 선언한 정책별 수락·수정·거부 건수 기록 |
| 스키마 필드 손상 | 사유를 남겨 격리·실패한 뒤 수정·재생 |
| 임시 체크포인트 유실 | 알려진 체크포인트 복원 또는 의도적으로 대조하는 재생 시작 |
| 소스 보존 기간 소진 | 복구 불가 공백 보고 또는 독립 소스 복사본에서 복원 |

입력률, 처리율, 이벤트→공개 지연, 상태 크기, 재시도, 마지막 체크포인트 이후 지난 시간, 출력 커밋을 함께 관찰한다. Kafka 지연 0도 마트 최신성을 입증하지 않는다. 하위 처리·공개가 멈췄을 수 있다.

## 실행 결과 예시

종합 프로젝트의 e1=100·e2=250을 사용한 가상 재생 장부이며 브로커 실행 트레이스가 아니다.

```text
input deliveries: e1, e2, e1
accepted unique IDs: e1, e2
published total_cents: 350
crash after sink commit before checkpoint: replay expected
after replay: unique IDs=2, total_cents=350
conflicting e1 payload: BLOCK or explicit quarantine
```

재생 합계 450은 이중 집계다. 공개가 멈췄는데 소스 지연만 0이면 신선도 실패다. 소스 보존과 독립 캡처에 모두 없는 이벤트는 체크포인트 재생성으로 복원할 수 없다.
