# 계보·카탈로그·거버넌스: 변경 영향과 접근 권한 확인하기

주문 테이블의 열 하나가 바뀌었다. 어떤 보고서가 영향을 받고, 담당자는 누구이며, 원본 데이터는 누가 읽을 수 있을까?

계보는 데이터가 어디에서 어떻게 만들어졌는지 연결한다. 카탈로그는 데이터셋을 찾고 의미를 이해하도록 돕는다. 접근 정책은 읽기와 변경 권한을 통제한다.

## 이 장에서 처음 쓰는 말

| 용어 | 의미 | 왜 필요한가요 · 언제 쓰나요 |
|---|---|---|
| job / run / dataset | 잡은 처리할 작업의 정의이고, 실행은 그 잡을 한 번 수행한 것이다. 데이터셋은 읽거나 쓰는 데이터 묶음이다. | 작업 정의, 이번 실행, 읽고 쓴 데이터를 구분해 문제 발생 지점을 찾는다. **구체적인 상황(가상 예시):** 일일 변환이 실패해 입력과 출력을 찾아야 한다. → 논리적 잡·이번 실행·관련 데이터셋을 구분한다. → 계보 이벤트의 식별자를 따라 영향을 받는 후속 데이터를 찾는다. |
| facet | OpenLineage의 잡·실행·데이터셋에 붙이는 추가 정보 묶음이다. 스키마 같은 정보를 일정한 형식으로 기록한다. | 기본 식별자만으로 부족한 스키마와 실행 정보를 정해진 형식으로 추가한다. **구체적인 상황(가상 예시):** 계보 이벤트에 기본 식별자 외의 스키마나 실행 정보가 필요하다. → 올바른 개체에 적절한 버전의 facet을 붙인다. → 소비자가 유형과 범위를 일관되게 해석하는지 확인한다. |
| 열 계보(column lineage) | 어느 입력 열이 어느 출력 열을 만드는 데 사용됐는지 나타내는 관계다. | 특정 열을 바꿨을 때 어떤 보고서의 어떤 값에 영향을 주는지 찾는다. **구체적인 상황(가상 예시):** 민감한 원본 열이 변환을 거쳐 여러 보고서에 들어갈 수 있다. → 수집된 열 계보와 변환 추적 범위를 살핀다. → 계측이 불완전한 부분은 실제 SQL에서 의존성을 확인한다. |
| RBAC / ABAC | RBAC는 역할로 접근 권한을 정한다. ABAC는 요청자·데이터·상황의 속성과 정책을 함께 사용한다. | 역할과 속성에 맞춰 허용할 읽기·쓰기를 정하고 실제로 시험한다. **구체적인 상황(가상 예시):** 팀 역할별 권한 외에 데이터 분류도 접근 판단에 필요하다. → 역할 기반·속성 기반 조건을 명시적으로 모델링한다. → 대표 신원으로 허용과 거부 조합을 시험한다. |
| 분류(classification) | 데이터를 공개·내부·민감 같은 범주로 나누는 일이다. 분류에 따라 처리 규칙을 적용한다. | 민감도에 따라 접근 권한과 보존·처리 규칙을 적용한다. **구체적인 상황(가상 예시):** 새 데이터셋에 제한적으로 다뤄야 할 연락처가 들어 있다. → 조직이 정의한 범주로 필드를 분류한다. → 후속 접근·보존 규칙이 그 분류를 사용하는지 확인한다. |
| 감사(audit) | 누가 자원에 접근하거나 관리 작업을 했고 무엇을 했는지 남긴 기록이다. | 누가 언제 어떤 데이터를 읽거나 바꿨는지 사후에 조사한다. **구체적인 상황(가상 예시):** 어제 제한 테이블을 누가 조회했는지 설명해야 한다. → 행위자를 식별할 수 있는 접근 감사 이벤트를 적절히 보호해 보존한다. → 기록으로 행위·사용자·대상·시각을 재구성한다. |

## 먼저 이해하기

1. 데이터셋·작업에 안정된 namespace/name 식별자를 준다.
2. 실행별 실제 입력·출력·상태·버전 정보를 기록한다.
3. 계보를 소유권·문서·분류·품질 결과와 연결한다.
4. 관계로 영향 후보를 찾는다.
5. 질의·저장·제공 경계에서 접근을 확인하고 결과를 감사한다.

OpenLineage 기본 모델은 데이터셋·작업·실행을 구분하고 facet으로 메타데이터를 확장한다. OTel span은 작업을 설명한다. 공통 실행 참조로 두 모델을 연결할 수 있지만 trace를 테이블 버전으로 취급하지 않는다. 실제 계보 관측 범위는 계측 범위에 달려 있다.

## 검토할 최소 이벤트

다음 가상 OpenLineage 이벤트는 완료된 변환을 보여 준다. 완전한 구현은 적절한 수명 주기 이벤트도 보내고 고정 스키마로 검증한다. 예시 생산자 URL은 실제 이벤트 생성기의 문서화된 신원으로 바꾼다.

```json
{
  "eventType": "COMPLETE",
  "eventTime": "2026-09-10T01:00:00Z",
  "run": {"runId": "0c847daa-238e-4eca-8054-5583bb212d29"},
  "job": {"namespace": "study", "name": "orders.clean"},
  "inputs": [{"namespace": "study", "name": "orders.raw"}],
  "outputs": [{"namespace": "study", "name": "orders.accepted"}],
  "producer": "https://example.org/study-emitter",
  "schemaURL": "https://openlineage.io/spec/2-0-2/OpenLineage.json"
}
```

아직 물리 스냅샷, 열 변환, 소유권, 이 데이터를 사용하는 프로그램이나 팀는 식별하지 않는다. 이름 세 개가 전부 담는다고 가정하지 말고 지원 facet·통제된 기록 참조를 추가한다. `COMPLETE` 이벤트도 계약·구현이 연결하지 않으면 품질 검사 통과를 입증하지 않는다.

## 담당자가 있는 카탈로그 메타데이터

| 메타데이터 | 사용자에게 필요한 이유 |
|---|---|
| 의미·행 단위·단위·시간 기준 | 문법은 맞지만 의미는 틀린 질의 방지 |
| 담당자·지원 경로 | 복구 책임자·팀 찾기 |
| 스키마·계약 버전 | 연동 호환성 확인 |
| 현재 공개·품질 상태 | 검색 가능한 것과 사용 가능한 데이터 구분 |
| 분류·사용 정책 | 허용 취급·목적 판단 |
| 입력·출력 계보와 범위 | 변경 조사와 영향 분석 누락 범위 표시 |
| 보존·폐기 예정 | 재현·전환·제거 계획 |

소수 데이터셋의 명시적 메타데이터부터 시작한다. 검색, 담당자 절차, 수집 연동, 규모가 서비스를 정당화하면 DataHub·OpenMetadata를 평가한다. Marquez는 OpenLineage 실행 관계 탐색의 대안이다. 기능 개수만 세지 말고 실제 연동·권한 모델로 비교한다.

## 거버넌스는 파생 데이터까지 따라간다

카탈로그에 “민감 데이터” 태그를 붙이는 것만으로 접근이 차단되지는 않는다. 실제 SQL 엔진과 저장소, 내보내기·캐시·검색 서비스에서 그 정책을 검사해야 한다. 행 필터와 열 마스킹은 실제 사용자의 계정으로 시험한다. 화면에서 기능을 숨겼더라도, 뒤에서 동작하는 서비스 계정에 넓은 권한이 있고 호출자별 제한을 확인하지 않으면 원본을 읽을 수 있다.

질의 권한과 메타데이터 발견 권한을 분리한다. 테이블 이름·계보도 민감한 업무 구조를 드러낼 수 있다. 허용·거부 읽기, 정책 변경, 내보내기, 담당자 변경을 감사하고 감사 기록 자체의 보존·접근도 설정한다.

데이터 정책으로 원본을 지우면 테이블 이력, 계산 결과를 저장한 데이터 마트, 응답 캐시, 임베딩, 캡처 프롬프트 등 관련 파생물을 찾는다. 적용 정책에 따라 삭제·만료·보존할 대상을 정한다. 엔지니어링 전파 실습이며 법적 보존 기간을 정하는 과정은 아니다.

## dataset·job·run·facet 식별자

데이터셋 ID는 운영·개발 같은 네임스페이스를 구분해야 한다. 표시 이름만으로는 모호하다. job은 변환 정의, run은 연동 규칙에 따른 실행 시도·수명 주기 인스턴스다. 재시도는 부모·논리 작업 관계를 유지하며 새 run ID를 쓸 수 있다. 같은 테이블 이름과 같은 데이터를 혼동하지 않도록 출력 스냅샷 ID도 함께 둔다.

START와 COMPLETE·FAIL 같은 적절한 수명 이벤트를 낸다. 지연·중복 도착이 가능하므로 백엔드는 식별자·순서를 대조해야 한다. COMPLETE 부재는 실패·실행 중·전송 유실일 수 있다. 원인을 정하기 전에 스케줄러·공개 기록과 비교한다.

facet은 기본 이벤트에 붙이는 구조화된 추가 정보다. 테이블의 열 정의는 dataset facet에, 코드 버전이나 이번 실행의 정보는 알맞은 job/run facet에 넣는다. 의미가 맞는 표준 facet이 있으면 그것을 사용한다. 직접 정의할 때는 이름과 스키마 주소를 안정적으로 유지한다. 아무 JSON이나 추가하면 다른 도구가 뜻을 해석할 수 있는 것은 아니다.

### 테이블 계보와 열 계보

`daily_revenue.total`을 `SUM(orders.amount_cents)`로 계산한다고 하자. 테이블 계보는 daily_revenue가 orders를 읽는다는 관계를 보여 준다. 열 계보는 total 계산에 amount_cents를 썼다는 것까지 보여 준다. `SELECT *`로 읽는 프로그램은 직접 계산하지 않는 열의 이름 변경에도 영향을 받을 수 있지만 필요한 열만 읽는 프로그램은 괜찮을 수 있다. 반대로 열 이름과 연결 관계가 같더라도 금액 단위가 바뀌면 결과의 뜻은 달라진다.

정적 SQL 분석은 잠재 의존성을, 런타임 계측은 실제 실행을 기록할 수 있다. 동적 SQL, UDF 내부, 파일 내보내기, 수동 복사는 양쪽 모두 공백을 남길 수 있다. 수집 범위를 명시하고 발생한 입력·출력 ID를 알려진 예제 그래프와 비교한다.

## 순환에 안전한 탐색으로 하위 영향 계산하기

다음 Python 예제는 명시적으로 선언한 가상 그래프를 탐색한다. 숨은 사용자를 발견하거나 데이터 진실성을 검증하지 않는다. 순환은 종료를 시험하기 위해 넣었고 정렬 출력으로 재현성을 확보한다.

<!-- executable: lineage-impact -->
```python
edges = {
    'raw': {'accepted'},
    'accepted': {'daily_revenue'},
    'daily_revenue': {'retrieval_index'},
    'retrieval_index': {'accepted'},
}
def descendants(start):
    seen, pending = {start}, [start]
    while pending:
        for node in edges.get(pending.pop(), set()):
            if node not in seen:
                seen.add(node)
                pending.append(node)
    return sorted(seen - {start})

found = descendants('raw')
assert found == ['accepted','daily_revenue','retrieval_index']
print('candidate_impact:', ', '.join(found))
print('coverage: declared edges only')
```

예상 출력:

```text
candidate_impact: accepted, daily_revenue, retrieval_index
coverage: declared edges only
```

그래프에서 연결 하나를 지우면 탐색 결과도 줄어든다. 하지만 실제 사용 프로그램이 사라진 것은 아니다. 찾은 데이터셋에 담당자와 사용처를 연결하고, 예정된 변경이 각 사용처의 데이터 규칙을 깨뜨리는지 확인한다. 계보 수집이 멈춘 상태를 알아볼 수 있도록 마지막으로 수집한 시점도 표시한다.

## RBAC·ABAC·마스킹·행·열 정책 강제

RBAC는 역할에 권한을 묶는다. 예를 들어 변환 역할은 정제 테이블에 쓰고, 조회 역할은 승인된 뷰를 읽으며, 관리 역할은 메타데이터를 바꾸게 한다. ABAC는 요청자의 부서나 데이터의 분류 같은 속성을 정책과 비교한다. 이 검사는 실제 조회·저장·제공 단계에서 실행돼야 한다. 사용자가 요청에 `department=finance`라고 썼다는 이유만으로 재무 권한을 주면 안 된다. 속성이 믿을 수 있는 곳에서 발급됐는지도 확인한다.

행 수준 보안은 보이는 레코드를, 열 권한은 민감 필드 선택을 제한하며 마스킹은 정책에 따라 표시값을 바꾼다. 같은 역할이 원본 테이블을 읽으면 뷰 마스크의 보호 효과는 작다. 공유 서비스 신원도 사용자 대신 행동할 때 호출자별 강제가 필요하다. 실제 소비자 신원으로 직접 테이블·뷰·내보내기·캐시·검색 엔드포인트를 시험한다.

PostgreSQL에서는 문서화된 조건에서 테이블 소유자·특권 역할이 RLS를 우회할 수 있다. 소유자로만 시험하면 소비자 정책이 입증되지 않는다. 임시 DB에서 비소유 읽기 역할로 허용 지역, 금지 지역, 금지 열 쿼리를 비교한다. 각각 허용 행, 금지 행 0개, 권한 오류가 예상된다. 별도 관리자 예제로 금지 행이 실제 존재함을 확인한다.

## 분류·PII·파생물 감사

분류는 필드·데이터셋의 취급 요구를 정한다. 자동 탐지는 이메일 같은 후보를 제안할 수 있지만 패턴이 업무 목적이나 완전한 민감도 분류를 확정하지 않는다. 안정된 ID의 해시는 여전히 연결 가능할 수 있어 해시됐다고 무제한 공유 가능하다고 보지 않는다. 드러날 수 있는 내용에 따라 집계·추출·임베딩·디버그 캡처에도 취급 결정을 전파한다.

감사 기록에는 주체, 행동, 자원·버전, 정책 결정, 시간, 연관 참조를 남긴다. 성공 읽기뿐 아니라 거부·정책 변경도 기록한다. 감시 대상 신원에서 감사 저장소를 보호하고 관측 경로를 시험한다. 감사는 무엇을 시도·허용했는지 답하며 그 자체로 금지 읽기를 막지는 않는다.

DataHub·OpenMetadata는 탐색, 소유권, 설명, 연동 메타데이터를 조직하고 Marquez는 OpenLineage 실행 그래프에 집중한다. 실제 수집 어댑터와 식별자 대조를 먼저 평가한다. 같은 데이터셋이 열 개로 중복 표현되면 UI 그래프가 풍부해 보여도 영향 분석과 담당자가 분산된다.

## 실패 실습과 해석

문서화한 사용자 둘을 가진 `raw -> accepted -> daily_revenue -> retrieval_index`를 만든다. 금액 단위를 깨뜨리는 변경을 넣고 후속 데이터셋 조회로 영향 후보·담당자를 찾은 뒤 계보 이벤트 생성기가 실제 변환을 수집했는지 확인한다. 이벤트 생성기 하나를 끄고 반복하면 누락 간선은 영향 없음이 아니라 관측 기록 누락으로 드러나야 한다.

읽기 권한이 있는 계정, 권한이 없는 계정, 파이프라인의 쓰기 계정으로 각각 시험한다. 첫 계정은 허용된 행·열만 읽을 수 있어야 하고, 두 번째 계정의 읽기는 차단돼야 한다. 쓰기 계정도 담당하지 않는 데이터셋에는 접근하지 못해야 한다. 각 시도가 감사 기록에 남는지 확인한 뒤, 원래 정책으로 복구하고 허용·거부를 다시 시험한다.

## 실행 결과 예시

영향·접근 검토 예시다.

```text
changed: raw
candidate descendants: accepted, daily_revenue, retrieval_index
documented consumers: 2
disabled emitter: INCOMPLETE COVERAGE
authorized reader: allowed permitted rows/columns
unauthorized reader: denied
pipeline writer on unrelated dataset: denied
```

이벤트 생성기를 끈 후 후속 데이터셋이 줄어도 실제 영향 범위가 작아진 것이 아니다. 정책 실습 통과에는 실제 신원별 실행과 감사 기록이 필요하다. 권한 취소 뒤 검색·디버그 경로도 재확인한다.
